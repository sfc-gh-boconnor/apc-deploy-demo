# AGENT.md

Agent/context guide for the **AI Product Costing (APC) Accelerator**. Read this first when working in this repo.

## What this project is

A Snowflake demo accelerator for **SAP product costing & profitability** at a pharmaceutical company. It simulates **raw SAP extracts**, engineers them through a **dbt medallion pipeline materialised as Dynamic Tables** into analysis-ready marts, then layers analytics, scenario modelling, ML forecasting, a semantic model, observability, and a multi-tab dashboard (with a grouped **Live Demo** section) plus a Cortex AI chat. The app reads the **dbt-engineered `DBT_ANALYTICS` marts**.

The dashboard ships in **two interchangeable variants with identical tabs and data**:

| Variant | Path | Stack | Deploy |
|---------|------|-------|--------|
| **React / App Runtime** | `app-ui/` | Next.js (App Router) on SPCS, Node Snowflake SDK | `snow app deploy` (snow CLI ≥ 3.19) |
| **Streamlit-in-Snowflake** | `streamlit/` | (Legacy) `streamlit_app.py`, container runtime | Not deployed — kept for backwards compatibility |

The **React app is the styling/behaviour source of truth**. Streamlit is legacy.

**Tabs (React, current):** Variance Analysis · Scenario Analysis · Profitability · **Sales Forecast** · Smart Insights · Ask Cortex AI · **Data Engineering** · Observability & Trust. The app opens on **Data Engineering** by default.

**Scenario integration:** Scenarios defined on the Scenario Analysis tab (API Cost Shock, Volume Drop, Energy Spike) flow through to **Sales Forecast** (revenue + margin overlay lines) and **Smart Insights** (variance shift banner) via the `/api/scenarios/forecast` and `/api/sales-forecast/scenario` routes. Both tabs have a scenario dropdown. All scenario impact reads from `ML_FEATURE_STORE."VARIANCE_FORECAST_FV$V1"`.

## Data model (key objects, all in `APC_DEPLOY_DB`)

- **Raw extract — `APC_DEPLOY_DB.SAP_RAW`** (genuinely messy SAP, the dbt pipeline's source; from `09`/`10`): `MATERIAL_LEDGER_DOC` (CKMLCR posting line items in **local currency**, incl. reversals/duplicates), `MBEW_RAW` (effective-dated standard), `KEPH_RAW` (coded component split), `MARA_RAW`/`T001W_RAW` (master), `TCURR_RAW` (FX, inverted GDATU).
- **Curated reference — `APC_DEPLOY_DB.SAP_BDC` + `APC_DEPLOY_DB.ANALYTICS`** (SAP-named clean tables + views): `PRODUCT_COST_SUMMARY` (3-way), `COST_COMPONENT_DETAIL`, `PRODUCT_PROFITABILITY`, `PRODUCT_RISK_SCORES`, `COST_ANOMALIES`, `VARIANCE_TREND_WITH_FORECAST`, `COST_BUDGET`, `SCENARIO_*`. Kept as the **reconciliation target** for the dbt pipeline + the **procedural ML** (`FORECAST`, `FORECAST_ACCURACY/_BACKTEST_DETAIL`) + scenario write-back.
- **dbt marts — `APC_DEPLOY_DB.DBT_ANALYTICS`** (from `dbt/apc` via `snow dbt`; **what the app reads**): all Dynamic Tables — `MART_PRODUCT_COST` (Actual/Budget/Standard 3-way), `MART_COST_BUDGET`, `MART_COST_COMPONENT_DETAIL` (9 components), `MART_PRODUCT_PROFITABILITY`, `MART_COST_ANOMALIES`, `MART_PRODUCT_RISK_SCORES`, `MART_VARIANCE_TREND_WITH_FORECAST`, `MART_PRODUCT_COST_MONTHLY`, `MART_ENERGY_COST_BRIDGE`. Built raw -> staging -> intermediate -> marts; reconciliation tests prove parity with the curated views (±0.05). ML training (`FORECAST`) stays procedural; the trend mart consumes its output. Scenarios stay on `ANALYTICS` (write-back).
- **Energy feed — `APC_DEPLOY_DB.ENERGY_MARKET.ENERGY_PRICE_INDICES`** (from `11`): LEBA-shaped synthetic energy prices (5 markets × 30 months) that drive the index-driven **Energy / Utilities** cost component (9th component, carved out of Manufacturing Overhead). dbt `stg_energy_prices` + seed `plant_energy_intensity` + `mart_energy_cost_bridge` derive energy $/unit (market price × plant MWh-intensity) — the external-index→costed-energy lineage. Columns mirror the real `EOSE.*` Marketplace listings; swap the `energy_market` source to the live share for real data. Scenario `ENERGY_COST_CHANGE_PCT` + the **Energy Spike** preset flex it.
- **Engineering — `APC_DEPLOY_DB.ENGINEERING`** (optional alt demo, from `08_data_engineering.sql`): hand-written medallion Dynamic Tables — the SQL-authored counterpart to the dbt pipeline.
- **ML Feature Store — `APC_DEPLOY_DB.ML_FEATURE_STORE`** (from `feature_store.ipynb`): Snowflake Feature Store with entities (`MATERIAL`, `COST_COMPONENT_PERIOD`), feature views as Dynamic Tables (`PRODUCT_RISK_FV`, `ANOMALY_DETECTION_FV`, `VARIANCE_FORECAST_FV`), versioned training datasets (`ANOMALY_TRAINING_DS`, `RISK_SCORING_DS`, `FORECAST_TRAINING_DS`), and registered models (`APC_ANOMALY_DETECTOR` — Isolation Forest, `APC_RISK_CLASSIFIER` — Gradient Boosting). Feature views auto-refresh daily; app reads risk scores from `PRODUCT_RISK_FV$V1`.
- **Cortex Agent — `APC_DEPLOY_DB.ANALYTICS.APC_RECONCILIATION_AGENT`** (from `sql/13_reconciliation_agent.sql`): Natural-language reconciliation assistant for finance/supply chain. Backed by `APC_DEPLOY_DB.DBT_ANALYTICS.APC_RECONCILIATION_SV` (4-table semantic view: `MART_PRODUCT_COST`, `MART_RATE_STABILITY`, `MART_VOLUME_ALIGNMENT`, `MART_COGM_EVOLUTION`). Answers questions about cost drivers, rate instability, demand misalignment, and cost evolution. Workspace dev files in `cortex_project/`.
- **Data model:** FY2024 + FY2025 monthly + FY2026 H1; **budget = prior-year same-month actual** (`COST_BUDGET`); standard resets annually from prior-year actual average (+3% FY2026). Cost-driver model (inflation drift, planned shutdowns, absorption, yield noise) + winter seasonality on respiratory lines (RX-9901/7890/1156).
- **Warehouse:** `APC_DEPLOY_WH` (XSMALL). **Narrative:** FY2026 — API price shock in April, Dunboyne (PL03) + Bangalore (PL05) yield crisis in May, partial recovery in June.

## Skills (`.cortex/skills/`)

All skills use the `apc-` prefix (namespaces them to this accelerator). The data-engineering set is designed for a data engineer working in a **Snowsight Workspace with Cortex Code** — the right tool for iterative, deployable data engineering.

|-------|---------|-----|
| `apc-deploy` | Deploy the full accelerator (data + app). Version-gates React vs Streamlit on snow CLI ≥/< 3.19. | write |
| `apc-cleanup` | Tear down all APC objects (`DROP DATABASE APC_DEPLOY_DB CASCADE`, warehouse, apps). Destructive. | write |
| `apc-explore-schema` | Inventory a schema: objects, sizes, dynamic-table health, lineage, suggested next steps. | read |
| `apc-data-quality` | Profile a table/view/schema and produce a data quality report with flagged issues + fixes. | read |
| `apc-new-pipeline` | Scaffold a new staging→curated→mart Dynamic Table pipeline for a source, then deploy it. | write |
| `apc-data-engineering` | Describe a change → CoCo edits SQL → validate → deploy → verify → commit. The core change-and-deploy loop. | write |
| `apc-dbt-demo` | Deploy + run the **primary** raw-SAP -> costed dbt pipeline (`dbt/apc`, project `apc`) via `snow dbt` into `APC_DEPLOY_DB.DBT_ANALYTICS` (Dynamic-Table marts the app reads); run build + reconciliation tests + docs. Prompts for external access integration if needed. | write |
| `apc-external-integration` | Interactive: prompts for host, port, names, then creates a network rule + external access integration. Use when dbt deploy or UDFs need outbound HTTPS. | write |

## Working conventions

- **Deployment variables**: `vars.yaml` in the repo root defines `database`, `warehouse`, and `warehouse_size`. Use `python deploy.py -f sql/XX.sql` (instead of `snow sql -f`) to run SQL templates — `deploy.py` reads `vars.yaml` and passes values as `-D` flags automatically. Override per-run: `python deploy.py -D "database=MY_DB" -f sql/01_setup.sql`. The React app reads `SNOWFLAKE_DATABASE` / `SNOWFLAKE_WAREHOUSE` env vars with the same defaults.
- **Deploy connection:** local work uses your named snow CLI connection (`-c <your-connection>`). In a Snowsight Workspace, omit `-c` (auth is implicit) and use relative paths.
- **Keep the two app variants in sync.** When changing one tab, mirror the layout/behaviour in the other. React is the reference.
- **Redeploy after edits (Workspace):**
  1. Edit files in `app-ui/components/` or `app-ui/app/api/`
  2. **Sync bundle:** `cp app-ui/components/*.tsx app-ui/output/bundle/components/` (the build picks up `output/bundle/`)
  3. Upload: `COPY FILES INTO @APC_DEPLOY_DB.ANALYTICS.AI_PRODUCT_COSTING_CODE/ FROM 'snow://workspace/USER$<USERNAME>.PUBLIC."apc-deploy-demo"/versions/live/app-ui/'`
  4. Build + deploy: `cd app-ui && snow app deploy --build-only && snow app deploy --deploy-only`
- **Redeploy after edits (Local):** `cd app-ui && snow app deploy -c <conn>` (handles upload + build + deploy in one step)
- **SQL object changes** require re-running the relevant `sql/NN_*.sql` file manually; they are not auto-applied by app deploys.
- **Never use a personal database** in `snowflake.yml` — must be `database: APC_DEPLOY_DB`, `schema: ANALYTICS`.
- **Git branch discipline for data-engineering changes:** `main` is the pristine accelerator **template** — never commit engineer changes to it. The write skills (`apc-new-pipeline`, `apc-data-engineering`) create/use a feature branch (`de/<summary>`), commit there, and leave merging to a PR.
- **Snowpark in Workspaces/SiS — use `get_active_session()`, never `Session.builder`.** Any Snowpark Python generated for a Workspace or Streamlit-in-Snowflake must reuse the existing session via `from snowflake.snowpark.context import get_active_session; session = get_active_session()`. Creating a new session with `Session.builder...create()` hijacks/breaks the active Workspace connection. To run SQL, prefer the `snowflake_sql_execute` tool or `snow sql`.

  **Why this matters (token expiry):** Workspaces provide a short-lived OAuth token at `/snowflake/session/token`. When you create a NEW connection (via `Session.builder`, `snowflake.connector.connect()`, `SnowflakeConnection()`, or `create_engine("snowflake://...")`), it opens a competing session against the same token — the platform then **revokes** the original token, immediately breaking the Workspace connection. The only safe pattern is reusing the existing session.

  **Enforced by a PreToolUse hook** (`.cortex/hooks/block-create-connection.sh`) that blocks any execution tool call containing connection-creation patterns. Blocked patterns:
  - `Session.builder...create()` (Snowpark)
  - `snowflake.connector.connect(...)` (Python connector)
  - `snowflake.snowpark.Session(...)` (Snowpark constructor)
  - `SnowflakeConnection(...)` (connector wrapper)
  - `create_engine("snowflake://...")` (SQLAlchemy)
  - `snowflake.connector.SnowflakeConnection` (direct class)

  **Activate the hook in a Workspace:** The hook is defined in `.cortex/hooks.json`. To activate:
  ```bash
  # From the workspace root — one-time setup:
  mkdir -p ~/.snowflake/cortex
  ABS_HOOK="$(pwd)/.cortex/hooks/block-create-connection.sh"
  sed "s|<ABS_PATH_TO_REPO>|$(pwd)|" .cortex/hooks.json > ~/.snowflake/cortex/hooks.json
  chmod +x "$ABS_HOOK"
  ```
  Once active, any Cortex Code session in this workspace will auto-block connection-creation attempts and show the correct `get_active_session()` pattern instead.

## Gotchas (learned the hard way)

- **`output/bundle/` must be synced with source files.** The App Runtime build picks up files from `app-ui/output/bundle/` — if you edit `components/Foo.tsx` but don't copy it to `output/bundle/components/Foo.tsx`, the deployed app won't reflect changes. Always sync after editing: `cp app-ui/components/*.tsx app-ui/output/bundle/components/`.
- **`COPY FILES FROM snow://workspace/...`** is the only way to upload to stages from a Workspace (S3 PUT is blocked). Works for any file type.
- **`sql/06_ml_insights.sql` and `sql/12_sales_forecast.sql` are legacy.** The Feature Store notebook (`feature_store.ipynb`) replaces them with versioned models in the Model Registry. The old scripts still work if needed but the app now reads from Feature Store views.
- **`PRODUCT_PROFITABILITY` is a dynamic table with internal `SUM()`s.** Wrapping it in another `SUM()` (even through subqueries) raises `Aggregate functions cannot be nested`. In the Streamlit app, read raw rows and aggregate in pandas instead.
- **Streamlit container runtime is strict about source encoding.** Keep `# -*- coding: utf-8 -*-` at line 1 of `streamlit_app.py`. A stray/unterminated triple-quoted string surfaces as a misleading `invalid character`/`unterminated string` SyntaxError far from the real line — check triple-quote balance.
- **`st.plotly_chart` needs a unique `key=`** when multiple charts share the same params, or it raises a duplicate-ID error.
- **`AI_COMPLETE` answers can come back JSON-quoted/escaped** — unwrap (strip surrounding quotes, replace `\n`) before rendering.
- **Plotly category order** follows trace-insertion order; set `categoryorder="array"` + `categoryarray=[...]` to force period order (P001..P006).
- `snow app status` / `snow app logs` are **not** valid; only `deploy`, `open`, `run`, `teardown` (+ `snow app events`).
- The `streamlit/output/` bundle is a build artifact and is gitignored — don't commit it.
- **Reloading data breaks Dynamic Table change-tracking.** Re-running `01/02/09/10/11` (`CREATE OR REPLACE`) on an existing account means a plain `snow dbt ... apc build` SKIPS unchanged-SQL marts and serves **stale** data (e.g. 8 cost components instead of 9). Always reload with **`snow dbt execute ... apc build --full-refresh`** (recreates every DT on the new base tables). Re-run `sql/04_scenarios.sql` afterward to reset the scenario presets if the live app edited them. Fresh installs are unaffected.
